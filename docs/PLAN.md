# План реалізації demo-booking

Демо-сайт бронювання готелю Riverwood на базі API віджета HMS Servio.
Особливість завдання: **спосіб виконання є частиною тесту** — інфраструктуру
підіймає агент (Claude/Codex), без ручного заходу на сервер.

## Вимоги ТЗ

| Вимога | Деталі |
|---|---|
| Репозиторій | GitHub, `demo-booking` |
| Агент | Claude або Codex, підключений до репо |
| Сервер | чиста віртуалка, налаштування лише через агента |
| Рантайм | Docker, доступ на `http://<SERVER_IP>:8080` |
| CI/CD | GitHub Actions, автодеплой при пуші в `main` |
| БД | Postgres |
| Адмінка | `/admin`, доступ `admin:demo` |

Функціональні кроки сайту: вибір дат і гостей → вибір номера (доступність з
API) → форма даних гостя → перехід на оплату (посилання віддає той самий API) →
збереження броні в БД + мікро-адмінка зі списком броней. Статус оплати не
моніторимо.

> ⚠️ **Тестові броні — тільки на березень 2027.** Це бойовий API живого готелю,
> кожна тестова бронь займає реальний номер.

> ⚠️ **Секрети.** Root-пароль до віртуалки прийшов у ТЗ відкритим текстом — його
> треба вважати скомпрометованим і змінити при першому вході (Фаза 8.1). У код,
> конфіги та репозиторій жодні креденшли не потрапляють: локально `.env`
> (у `.gitignore`), у CI — GitHub Secrets, на сервері — `.env` поруч з compose.

## Прийнятий порядок робіт

SQLite спочатку, Postgres і Docker — в кінці. Це безпечно **рівно за однієї
умови**: конфіг БД env-driven з першого дня (`DATABASE_URL`), і жодних PG-only
полів у моделях. Тоді перехід на Postgres — зміна однієї змінної оточення, а не
рефакторинг. Саме тому Фаза 0.4 виконується до написання будь-якого коду.

Другий важливий момент порядку: **Фаза 1 (розвідка API) — перша**, бо її
результат може змінити архітектуру решти.

## Фаза 4 — UI бронювання ✅ ВИКОНАНО

Django templates, **без JS-фреймворку і без CDN** — класичний
POST/redirect/GET. Єдиний скрипт (14 рядків інлайном) блокує повторний
сабміт, бо пошук у Servio відповідає ~9 с.

| Крок | URL | Що робить | Стан |
|---|---|---|---|
| 1 | `/` | дати + гості, дефолт 10–12.03.2027 | session |
| 2 | `/rooms/` | оффери з API, ціни, залишок | session |
| 3 | `/guest/` | форма гостя + валідація | session |
| 4 | POST `/guest/` | `/rooms` → `/book` → `/payment-info` → `/make-payment` | **DB** |
| — | `/done/<pk>/` | бронь + оплата, якщо редіректу немає | — |

Реалізовано: [views.py](../booking/views.py), [forms.py](../booking/forms.py),
[session.py](../booking/session.py), [urls.py](../booking/urls.py),
шаблони в `booking/templates/booking/`.

**Що виявилось важливим по ходу:**

- **Порядок запису.** Бронь у БД зберігається **до** спроби оплати. Якщо
  оплата зірветься, номер у готелі вже зайнятий — слід мусить залишитись.
  Статус тоді `failed`, текст помилки — у `raw_response`
- **Перевалідація на кроці 4.** Перед `/book` доступність перезапитується.
  Номер розібрали → назад на крок 2; ціна змінилась → назад на крок 3 з
  попередженням, бронь не створюється
- **Захист від подвійного сабміту** на рівні сесії: у живому готелі другий
  клік — це друга зайнята кімната
- **Валідація вікна дат:** форма пускає тільки березень 2027, як вимагає ТЗ
- Картинки Servio віддаються по `http://` → нормалізуються в `https://`,
  інакше під HTTPS вони зникли б як mixed content
- `status = confirmed` сайт не виставляє: оплату ми не моніторимо, тож
  підтвердити бронь може лише готель у HMS

### Вікно на оплату — 20 хвилин (додано на прохання власника)

Неоплачена бронь через `PAYMENT_WINDOW_MINUTES` (дефолт 20) переходить у
новий статус `expired` — «Відхилена, час на оплату вийшов», і сайт більше не
веде на оплату.

**Межа можливого, яку треба знати.** Посилання на платіж живе на боці Servio
(`pay.riverwood.com.ua/...`) і **відкликати його ми не можемо**. Заборона
працює лише через наш сайт: після дедлайну ми не віддаємо URL. Якщо гість
уже скопіював посилання, Servio його прийме, поки не спрацюють власні
правила готелю (`saleRestrictions.minPay`). Це обмеження чужого API, не
нашої реалізації.

Друга межа: **«не оплачено» ми не знаємо**. Статус оплати за ТЗ не
моніториться, тому `expired` означає рівно «вікно закінчилось, а
підтвердження ми не отримали» — це рішення власника, а не сигнал платіжного
сервісу. Гість, який оплатив на 19-й хвилині, все одно побачить відхилення,
якщо не встиг повернутися на сайт.

Як зроблено:

| Частина | Деталі |
|---|---|
| Дедлайн | `Booking.payment_deadline` = `created_at` + вікно; `is_payable` |
| Гейт оплати | окремий вʼю `/pay/<pk>/` — крок 4 і сторінка броні йдуть через нього, прямого посилання на Servio у HTML немає |
| Автоматика | команда `expire_bookings` + сервіс `scheduler` у compose, раз на 60 с |
| Страховка | ліниве протермінування при відкритті сторінки — правда показується навіть якщо планувальник лежить |
| Адмінка | показує дедлайн і залишок; посилання після дедлайну стає неклікабельним |

`scheduler` — окремий сервіс на тому ж образі з `while true; sleep`, а не
cron: у slim-образі cron немає, а ставити його заради одного завдання — зайва
сутність.

Покрито 31 тестом у [test_payment_window.py](../tests/test_payment_window.py),
включно з тим, що команда **не звертається до Servio** і що протермінована
бронь не віддає URL ні на сторінці, ні в адмінці.

**Перевірено:** 87 тестів (49 клієнт + 38 флоу). Плюс прогін у справжньому
Chrome проти живого API: кроки 1–3, 11 карток з цінами і залишком, валідація
обох форм, вхід в адмінку, нуль JS-помилок. Крок 4 у браузері не виконувався —
`/book` і `/make-payment` були заблоковані на рівні перехоплення запитів, щоб
не створити реальну бронь.

### Початковий план фази

**Стек:** Django templates + HTMX/vanilla JS. Без SPA — це прибирає node-білд з
Docker-образу і з CI, а для 4 кроків React не дає нічого.

| Крок | Що робить | Стан |
|---|---|---|
| 1 | Дати + гості, дефолт — березень 2027 | session |
| 2 | Список номерів з API, ціни, залишок | session |
| 3 | Форма даних гостя + валідація | session |
| 4 | Створення броні → запис у БД → редірект на оплату | **DB** |

**Ключове рішення:** до кроку 4 в БД нічого не пишемо — тримаємо в сесії. Інакше
база засмічується покинутими чернетками.

**Валідація:** `check_out > check_in`, дати не в минулому, розумний максимум
ночей, обов'язковий email/телефон.

**Обробка помилок, які точно будуть:** API недоступний; номер розібрали між
кроком 2 і 4; бронь відхилена; немає посилання на оплату.

### Рішення фази

- **`config/settings_test.py`** замість `conftest.py`: pytest-django піднімає
  Django ще до того, як імпортується кореневий `conftest.py`, тож виставити
  там `SECRET_KEY` неможливо. Модуль лише підставляє дефолти оточення **до**
  імпорту справжніх settings — власне налаштування там одне, швидкий хешер
  паролів (він зрізав прогін з 12 с до 2 с)
- **Ключі Servio в тестах підставні** (`SERVIO_API_BASE=https://servio.invalid`):
  жоден тест не має шансу піти в живий готель, навіть помилково
- **`ruff format` не додаю** — він переписав би лапки в усьому коді, це не
  задача цієї фази. Тільки лінт

- CI додатково перевіряє `manage.py check` і **`makemigrations --check`** —
  щоб не поїхала модель без міграції
- **`uv sync --frozen`**: збірка падає, якщо `uv.lock` розійшовся з
  `pyproject.toml`

- Юніт-тести: клієнт Servio, форми, модель

- Міграції накатались на **порожню базу з нуля**, 19 міграцій, без помилок

Додано тест-охоронець `test_no_postgres_only_fields`: якщо колись у моделі
з'явиться поле з `django.contrib.postgres`, тест впаде — портативність
перестане бути домовленістю на словах.

### Що показала перша реальна бронь

Вона зловила два справжні баги, яких не бачив жоден із 132 тестів — бо оба
жили в припущеннях про чужий API, а не в нашому коді.

**1. `/make-payment` відповідає HTTP 307.** `httpx` за замовчуванням редіректи
не слідує, тож клієнт отримав тіло редіректу замість JSON і кинув
`ServioProtocolError`. У браузері це не видно: `fetch()` слідує редіректам
сам. Виправлено `follow_redirects=True`. Для POST безпечно саме тому, що код
307 — він зберігає метод і тіло, а оригінальний запит сервером ще не
обробляється; був би 302, httpx перетворив би POST на GET.

**2. Servio валідує телефон суворіше за нашу форму.** Перша спроба впала з
`isError: true`, `message: "Невірний формат номера телефону"`. Приймається
лише «+» і цифри підряд; наша регулярка пропускала пробіли, дужки й дефіси.
Виправлено нормалізацією у формі: користувач пише як звик, у Servio їде
E.164. Місцевий формат `044…` перетворюється на `+38044…`.

Тут же підтвердилось найважливіше архітектурне рішення фази: **бронь
збереглася, хоч оплата впала**. Номер у готелі був уже зайнятий, і слід не
зник — статус `failed`, текст помилки в `raw_response`. Зворотний порядок
запису втратив би реальну бронь.

### Знята невідомість по оплаті

`paymentService` у Riverwood — **4**, тобто звичайний редірект на `data.url`,
без платіжного віджета й підпису мерчанта (`useIFrame: false`). Відповідь
`/make-payment` містить рівно `{paymentServiceID, url}`. Посилання виду
`https://pay.riverwood.com.ua/api/v1/checkout/<uuid>/form`.

Ще одне уточнення: **`/book` уже віддає `paymentInfo`** з `services` і
`paymentServices`, тож окремий GET `/payment-info` не обов'язковий. Тепер він
використовується лише як запасний шлях. І `paymentService` треба надсилати
явно — ми спершу надсилали `null`, віджет так не робить.

Деталі контракту — у [servio-api.md](servio-api.md).

### Рішення й знахідки

- **`/healthz` зроблено тут, а не у Фазі 9.** Без нього ні healthcheck
  контейнера, ні compose `depends_on` не мають на що дивитись. Перевіряє БД
  (застосунок без Postgres «живим» не вважається), але **не** чіпає Servio:
  недоступність чужого API не має валити наш деплой
- **`--timeout 120` у gunicorn.** Дефолтні 30 с убивали б воркер посеред
  створення броні: пошук у Servio відповідає ~9 с, а крок 4 робить три
  послідовних виклики до нього
- **`CompressedStaticFilesStorage`, а не Manifest-варіант.** Manifest
  жорстко падає на відсутньому манифесті — це ламало б і тести, і будь-який
  `runserver` до `collectstatic`. Кеш-бастингу немає, для демо не критично
- **uv копіюється з `ghcr.io/astral-sh/uv:0.12.10`** у звичайний
  `python:3.14-slim`, замість тега `uv:python3.14-*`, якого може не існувати
  для свіжого Python. Обидві стадії на однаковому тезі Python — venv несе
  абсолютні шляхи
- **`libpq` в образ не ставиться:** `psycopg[binary]` несе його в собі
- **`.gitattributes` з `eol=lf`.** На машині розробки `core.autocrlf=true`,
  тож git при наступному checkout зробив би з `entrypoint.sh` CRLF — і
  контейнер падав би на шебангу з «no such file or directory»
- **`WEB_IMAGE`** у compose дає Фазі 9 підставити образ із GHCR замість
  збірки на сервері, не переписуючи compose
- Обов'язкові змінні в compose оголошені як `${VAR:?}` — стек не піднімається
  без `SECRET_KEY`, `POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, `ALLOWED_HOSTS`,
  `SERVIO_COMPANY_KEY`, `SERVIO_HOTEL_ID`. Краще впасти одразу, ніж
  піднятися з дефолтним паролем

### Чому один крок не автоматизується

Агент не працює з паролями. Щоб він зайшов, на сервері спершу має з'явитися
його публічний ключ, а для цього потрібен той самий пароль. Тому крок 0 у
[deploy/README.md](../deploy/README.md) — одна команда, яку виконує людина.
Далі все по ключу, без жодного секрету в моїх руках.

### Рішення власника: root-пароль лишається

Пароль із ТЗ **не змінюється і не блокується** — так вирішив власник
проєкту. Тому `harden.sh` перероблений: за замовчуванням він нічого не
забирає, лише гарантує `PubkeyAuthentication yes` і друкує стан sshd.
Вимкнення парольного входу (`DISABLE_PASSWORD_AUTH=yes`) і блокування
пароля root (`LOCK_ROOT=yes`) стали опційними.

Наслідок, який варто тримати в голові: пароль, що їздив у PDF, лишається
діючим креденшлом на публічному порту 22. Прикриває це `ufw` (тільки 22 і
8080) і те, що застосунок працює під окремим користувачем `deploy` без
пароля. Ключ уже буде на місці, тож закрити парольний вхід можна однією
командою в будь-який момент.
