# План реалізації demo-booking

Демо-сайт бронювання готелю Riverwood на базі API віджета HMS Servio.
Особливість завдання: **спосіб виконання є частиною тесту** — інфраструктуру
підіймає агент (Claude/Codex), без ручного заходу на сервер.

## Вимоги ТЗ

| Вимога | Деталі |
|---|---|
| Репозиторій | GitHub, `demo-booking` |
| Агент | Claude або Codex, підключений до репо |
| Сервер | чиста віртуалка, налаштування лише через агента |
| Рантайм | Docker, доступ на `http://<SERVER_IP>:8080` |
| CI/CD | GitHub Actions, автодеплой при пуші в `main` |
| БД | Postgres |
| Адмінка | `/admin`, доступ `admin:demo` |

Функціональні кроки сайту: вибір дат і гостей → вибір номера (доступність з
API) → форма даних гостя → перехід на оплату (посилання віддає той самий API) →
збереження броні в БД + мікро-адмінка зі списком броней. Статус оплати не
моніторимо.

> ⚠️ **Тестові броні — тільки на березень 2027.** Це бойовий API живого готелю,
> кожна тестова бронь займає реальний номер.

> ⚠️ **Секрети.** Root-пароль до віртуалки прийшов у ТЗ відкритим текстом — його
> треба вважати скомпрометованим і змінити при першому вході (Фаза 8.1). У код,
> конфіги та репозиторій жодні креденшли не потрапляють: локально `.env`
> (у `.gitignore`), у CI — GitHub Secrets, на сервері — `.env` поруч з compose.

## Прийнятий порядок робіт

SQLite спочатку, Postgres і Docker — в кінці. Це безпечно **рівно за однієї
умови**: конфіг БД env-driven з першого дня (`DATABASE_URL`), і жодних PG-only
полів у моделях. Тоді перехід на Postgres — зміна однієї змінної оточення, а не
рефакторинг. Саме тому Фаза 0.4 виконується до написання будь-якого коду.

Другий важливий момент порядку: **Фаза 1 (розвідка API) — перша**, бо її
результат може змінити архітектуру решти.

## Фаза 4 — UI бронювання ✅ ВИКОНАНО

Django templates, **без JS-фреймворку і без CDN** — класичний
POST/redirect/GET. Єдиний скрипт (14 рядків інлайном) блокує повторний
сабміт, бо пошук у Servio відповідає ~9 с.

| Крок | URL | Що робить | Стан |
|---|---|---|---|
| 1 | `/` | дати + гості, дефолт 10–12.03.2027 | session |
| 2 | `/rooms/` | оффери з API, ціни, залишок | session |
| 3 | `/guest/` | форма гостя + валідація | session |
| 4 | POST `/guest/` | `/rooms` → `/book` → `/payment-info` → `/make-payment` | **DB** |
| — | `/done/<pk>/` | бронь + оплата, якщо редіректу немає | — |

Реалізовано: [views.py](../booking/views.py), [forms.py](../booking/forms.py),
[session.py](../booking/session.py), [urls.py](../booking/urls.py),
шаблони в `booking/templates/booking/`.

**Що виявилось важливим по ходу:**

- **Порядок запису.** Бронь у БД зберігається **до** спроби оплати. Якщо
  оплата зірветься, номер у готелі вже зайнятий — слід мусить залишитись.
  Статус тоді `failed`, текст помилки — у `raw_response`
- **Перевалідація на кроці 4.** Перед `/book` доступність перезапитується.
  Номер розібрали → назад на крок 2; ціна змінилась → назад на крок 3 з
  попередженням, бронь не створюється
- **Захист від подвійного сабміту** на рівні сесії: у живому готелі другий
  клік — це друга зайнята кімната
- **Валідація вікна дат:** форма пускає тільки березень 2027, як вимагає ТЗ
- Картинки Servio віддаються по `http://` → нормалізуються в `https://`,
  інакше під HTTPS вони зникли б як mixed content
- `status = confirmed` сайт не виставляє: оплату ми не моніторимо, тож
  підтвердити бронь може лише готель у HMS

**Перевірено:** 87 тестів (49 клієнт + 38 флоу). Плюс прогін у справжньому
Chrome проти живого API: кроки 1–3, 11 карток з цінами і залишком, валідація
обох форм, вхід в адмінку, нуль JS-помилок. Крок 4 у браузері не виконувався —
`/book` і `/make-payment` були заблоковані на рівні перехоплення запитів, щоб
не створити реальну бронь.

### Початковий план фази

**Стек:** Django templates + HTMX/vanilla JS. Без SPA — це прибирає node-білд з
Docker-образу і з CI, а для 4 кроків React не дає нічого.

| Крок | Що робить | Стан |
|---|---|---|
| 1 | Дати + гості, дефолт — березень 2027 | session |
| 2 | Список номерів з API, ціни, залишок | session |
| 3 | Форма даних гостя + валідація | session |
| 4 | Створення броні → запис у БД → редірект на оплату | **DB** |

**Ключове рішення:** до кроку 4 в БД нічого не пишемо — тримаємо в сесії. Інакше
база засмічується покинутими чернетками.

**Валідація:** `check_out > check_in`, дати не в минулому, розумний максимум
ночей, обов'язковий email/телефон.

**Обробка помилок, які точно будуть:** API недоступний; номер розібрали між
кроком 2 і 4; бронь відхилена; немає посилання на оплату.

- [x] Інтеграційний: весь флоу з замоканим клієнтом (38)
- [x] GitHub Actions на кожен push у `main` і кожен PR

**128 тестів, 2 секунди, ruff чистий.** Прогін локально тими самими
командами, що й у CI.

### Як запускати

```powershell
uv run pytest -q                 # тести
uv run ruff check .              # лінт
uv run python manage.py test --settings=config.settings_test   # теж працює
```

Тести написані на `SimpleTestCase`/`TestCase`, тому йдуть і під pytest, і під
штатним раннером Django — переписувати нічого не довелось.

### Рішення фази

- **`config/settings_test.py`** замість `conftest.py`: pytest-django піднімає
  Django ще до того, як імпортується кореневий `conftest.py`, тож виставити
  там `SECRET_KEY` неможливо. Модуль лише підставляє дефолти оточення **до**
  імпорту справжніх settings — власне налаштування там одне, швидкий хешер
  паролів (він зрізав прогін з 12 с до 2 с)
- **Ключі Servio в тестах підставні** (`SERVIO_API_BASE=https://servio.invalid`):
  жоден тест не має шансу піти в живий готель, навіть помилково
- **`ruff format` не додаю** — він переписав би лапки в усьому коді, це не
  задача цієї фази. Тільки лінт
- **`RUF012` вимкнено**: спрацьовує на `Meta.ordering`/`constraints`/`indexes`,
  де `ClassVar` нічого не дає
- CI додатково перевіряє `manage.py check` і **`makemigrations --check`** —
  щоб не поїхала модель без міграції
- **`uv sync --frozen`**: збірка падає, якщо `uv.lock` розійшовся з
  `pyproject.toml`

### Початковий план фази

- `pytest` + `pytest-django`, `ruff` для лінту
- Юніт-тести: клієнт Servio, форми, модель
- Інтеграційний: весь флоу з замоканим клієнтом
- GitHub Actions: `ruff check` + `pytest` на кожен push і PR

На цьому етапі CI ганяє SQLite — швидко і дешево. Postgres додаємо наступною фазою.

## Фаза 8 — Сервер (0.5 дня, через агента по SSH)

**8.1 Безпека — перед усім іншим:**
- Змінити root-пароль з ТЗ (він скомпрометований)
- Додати SSH-ключ, вимкнути парольний вхід
  (`PermitRootLogin prohibit-password`, `PasswordAuthentication no`)
- `ufw`: дозволити тільки 22 і 8080

**8.2** Встановити Docker Engine + compose plugin
**8.3** `/opt/demo-booking`, `.env` з секретами — файл живе тільки на сервері
**8.4** Перший деплой руками агента → перевірити `http://<SERVER_IP>:8080`

## Фаза 9 — Автодеплой GitHub Actions (0.5 дня)

**9.1 Secrets:** `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `DJANGO_SECRET_KEY`,
`POSTGRES_PASSWORD`

**9.2 Пайплайн на push у `main`:**
```
lint → test (Postgres service) → docker build → push у GHCR
  → SSH: pull → compose up -d → migrate → health check
```

**9.3** Health-check ендпоінт `/healthz` — щоб деплой падав, якщо застосунок не
піднявся, а не «зеленів» наосліп.
