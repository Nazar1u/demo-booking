# План реалізації demo-booking

Демо-сайт бронювання готелю Riverwood на базі API віджета HMS Servio.
Особливість завдання: **спосіб виконання є частиною тесту** — інфраструктуру
підіймає агент (Claude/Codex), без ручного заходу на сервер.

## Вимоги ТЗ

| Вимога | Деталі |
|---|---|
| Репозиторій | GitHub, `demo-booking` |
| Агент | Claude або Codex, підключений до репо |
| Сервер | чиста віртуалка, налаштування лише через агента |
| Рантайм | Docker, доступ на `http://<SERVER_IP>:8080` |
| CI/CD | GitHub Actions, автодеплой при пуші в `main` |
| БД | Postgres |
| Адмінка | `/admin`, доступ `admin:demo` |

Функціональні кроки сайту: вибір дат і гостей → вибір номера (доступність з
API) → форма даних гостя → перехід на оплату (посилання віддає той самий API) →
збереження броні в БД + мікро-адмінка зі списком броней. Статус оплати не
моніторимо.

> ⚠️ **Тестові броні — тільки на березень 2027.** Це бойовий API живого готелю,
> кожна тестова бронь займає реальний номер.

> ⚠️ **Секрети.** Root-пароль до віртуалки прийшов у ТЗ відкритим текстом — його
> треба вважати скомпрометованим і змінити при першому вході (Фаза 8.1). У код,
> конфіги та репозиторій жодні креденшли не потрапляють: локально `.env`
> (у `.gitignore`), у CI — GitHub Secrets, на сервері — `.env` поруч з compose.

## Прийнятий порядок робіт

SQLite спочатку, Postgres і Docker — в кінці. Це безпечно **рівно за однієї
умови**: конфіг БД env-driven з першого дня (`DATABASE_URL`), і жодних PG-only
полів у моделях. Тоді перехід на Postgres — зміна однієї змінної оточення, а не
рефакторинг. Саме тому Фаза 0.4 виконується до написання будь-якого коду.

Другий важливий момент порядку: **Фаза 1 (розвідка API) — перша**, бо її
результат може змінити архітектуру решти.

### Змінні оточення

| Змінна | Локально (dev) | На сервері |
|---|---|---|
| `SECRET_KEY` | з `.env` | GitHub Secrets |
| `DEBUG` | `True` | `False` (дефолт) |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | `<SERVER_IP>` |
| `CSRF_TRUSTED_ORIGINS` | — | `http://<SERVER_IP>:8080` |
| `DATABASE_URL` | `sqlite:///db.sqlite3` (дефолт) | `postgres://…` |
| `SERVIO_API_BASE` | однаково | однаково |
| `SERVIO_HOTEL_ID` | однаково | однаково |
| `SERVIO_TIMEOUT` | `15` | `15` |

`CSRF_TRUSTED_ORIGINS` потрібен, бо на нестандартному порту Django перевіряє
`Origin` у формі логіну адмінки — без нього вхід на `:8080` не працює.

### Локальний старт

```powershell
Copy-Item env.example .env
# згенерувати SECRET_KEY і вписати в .env:
uv run python -c "from django.core.management.utils import get_random_secret_key as k; print(k())"
uv sync
uv run manage.py migrate
uv run manage.py runserver
```

## Фаза 1 — Розвідка API Servio (1 день) 🔴 найризикованіша

**1.1** Зняти трафік: `riverwood.com.ua/booking/` → DevTools → Network →
фільтр `servio`. Пройти весь шлях **на дати березня 2027**, зупинившись перед
фінальним підтвердженням броні.

**1.2** Задокументувати ланцюжок викликів. По кожному ендпоінту: URL і метод;
обов'язкові заголовки (чи потрібен API-ключ, hotel ID, чи перевіряється
`Origin`/`Referer`); формат запиту і відповіді (структура `{isError, message,
data}`); формат помилок.

Мінімальний набір, який треба знайти:
1. Список/конфіг типів номерів готелю
2. Пошук доступності — дати + гості → номери, ціни, залишок
3. Створення броні — payload з даними гостя
4. Отримання посилання на оплату

**1.3** Рішення по CORS. Якщо API віддає дозвільний `Access-Control-Allow-Origin`,
технічно можна кликати з браузера. **Рекомендація — проксі через Django в
будь-якому разі:** ключі не світяться в браузері, є логування, і ми не залежимо
від CORS-політики чужого сервісу.

**1.4** Зберегти реальні JSON-відповіді у `tests/fixtures/servio/*.json` — на них
далі будуються всі тести без мережі.

**Правило фази:** тільки read-only виклики. Жодної реальної броні до Фази 7.

**Результат:** `docs/servio-api.md` з описом контракту + фікстури.

## Фаза 2 — Модель даних і адмінка (0.5 дня, SQLite)

**2.1** App `booking`.

**2.2** Модель `Booking`, поля чотирма групами:

- *Пошук:* `check_in`, `check_out`, `adults`, `children`
- *Номер:* `room_type_id`, `room_name`, `price`, `currency`
- *Гість:* `guest_name`, `guest_email`, `guest_phone`, `comment`
- *Інтеграція:* `servio_booking_id`, `payment_url`, `status`,
  `raw_request`/`raw_response` (`models.JSONField` — портативний,
  працює однаково в SQLite і PG), `created_at`

Статуси мінімальні, бо оплату не моніторимо: `pending` → `confirmed` → `failed`.
Зберігати сирі payload'и в JSON — критично для дебагу чужого API.

**2.3** Адмінка: `list_display` з датами/гостем/сумою, фільтри по статусу і
датах, пошук по email/прізвищу, клікабельне посилання на оплату, `readonly` на
всіх полях — це журнал, а не форма редагування.

**2.4** Ідемпотентна management-команда `ensure_admin`, що читає логін/пароль з
env (`admin:demo`). Потрібна, бо за умовами ТЗ на деплої створювати юзера руками
не можна.

## Фаза 4 — UI бронювання, 4 кроки (1.5 дня)

**Стек:** Django templates + HTMX/vanilla JS. Без SPA — це прибирає node-білд з
Docker-образу і з CI, а для 4 кроків React не дає нічого.

| Крок | Що робить | Стан |
|---|---|---|
| 1 | Дати + гості, дефолт — березень 2027 | session |
| 2 | Список номерів з API, ціни, залишок | session |
| 3 | Форма даних гостя + валідація | session |
| 4 | Створення броні → запис у БД → редірект на оплату | **DB** |

**Ключове рішення:** до кроку 4 в БД нічого не пишемо — тримаємо в сесії. Інакше
база засмічується покинутими чернетками.

**Валідація:** `check_out > check_in`, дати не в минулому, розумний максимум
ночей, обов'язковий email/телефон.

**Обробка помилок, які точно будуть:** API недоступний; номер розібрали між
кроком 2 і 4; бронь відхилена; немає посилання на оплату.

## Фаза 6 — Перехід на Postgres (0.5 дня)

Завдяки Фазі 0.4 це майже виключно конфіг.

**6.1** `uv add "psycopg[binary]"`
**6.2** Змінити `DATABASE_URL` — код не чіпаємо
**6.3** Локального Docker на машині немає і без прав адміністратора не буде, тому
**CI стає місцем перевірки Postgres:** у GitHub Actions додаємо
`services: postgres:17` і ганяємо весь тест-сьют проти справжньої PG. Локально
лишається SQLite для швидкої розробки.
**6.4** Перевірити сумісність: жодних PG-only полів, `JSONField` —
портативний `models.JSONField`, міграції накатуються на чисту PG з нуля.

## Фаза 7 — Dockerization (1 день)

**7.1** `Dockerfile`, multi-stage:
- Builder: `uv sync --frozen --no-dev` (використовуємо наявний `uv.lock`)
- Runtime: slim-образ, non-root user, `gunicorn`, `whitenoise` для статики

**7.2** `docker-compose.yml`: `web` + `postgres` + volume для даних, порт `8080:8000`

**7.3** `entrypoint.sh`: `migrate` → `collectstatic` → `ensure_admin` → `gunicorn`

**7.4** `.dockerignore` — обов'язково, інакше `.venv` і `.git` поїдуть в образ

**7.5** Локально зібрати не вийде → job `docker build` у CI ловить помилки збірки
ще до сервера

**7.6** **Перша реальна бронь** — тут, на березень 2027, один раз, наскрізь до
сторінки оплати
